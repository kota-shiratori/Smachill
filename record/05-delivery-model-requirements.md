# 受け渡しモデルを配送一本に確定し、占有期間を引き直す

期間: 2026-09-04

## 何をしたか

実装（8/20〜8/30）が進んだ結果、**事業モデルとスキーマがズレたまま動いている**ことが分かった。
要件定義に一度差し戻して受け渡しモデルを確定させ、そこから占有期間の定義をやり直した。

コードを書く前に決めたのは4つ。

| 決めたこと | 結論 |
|---|---|
| 受け渡し方法 | **配送一本**。対面手渡しは扱わない |
| 返却後の整備 | **1日**。返送到着の翌日は次に出せない |
| 日帰りレンタル | **受け付ける**（use_start = use_end） |
| 配送対応エリア | **関東〜東海**（12都県）。北海道・福岡・大阪は v1 から外す |

---

## 決定の理由とトレードオフ

### 1. 配送一本にした

**結論**: 受け渡し方法という軸をシステムに持たせない。`shipping_zones` に行がある都道府県が対象エリア、無ければ 404。

**理由**: 手渡しを併存させると `bookings` に `delivery_method` が必要になり、占有期間の計算が受け渡し方法で分岐する。
配送一本なら「配送日数がそのまま在庫ロックになる」というこのシステムの中心が一本の式で書ける。

**トレードオフ**: 東京の顧客にも送料がかかる。近距離ほど不利になるので、
手渡しを商売として復活させるなら `days = 0 / fee = 0` のゾーンを1行足すのが最小の変更になる
（占有計算のコードは1行も変えずに済む）。そこは残してある。

### 2. `plans.turnaround_days` を足した

**結論**: 返送到着日の**翌日から** `turnaround_days` 日ぶんを `MAINTENANCE` として `item_days` に書く。

**理由**: テントサウナは濡れて戻るので、到着当日にそのまま次へ出せない。
これまで占有は「発送〜返送到着」までで終わっていたため、**返送到着の翌日を次の予約の発送日に売れてしまっていた**。
実機1台で月6件を回す事業設計では、これは月の回転数を直接壊す。

**なぜ `shipping_zones` ではなく `plans` に置いたか**: 乾燥にかかる時間は機材の性質であって、
配送先の性質ではない。千葉に送っても愛知に送っても、濡れ方は変わらない。

**トレードオフ**: 実機ごとに乾燥速度が違う場合（屋内保管と屋外保管など）は表現できない。
個体差が出たら `inventory_items` 側に移すことになるが、現状1台なので分けない。

### 3. 「泊」をやめて「日」で数える

**結論**: `plans.nights` → `included_days`、`extra_night_price` → `extra_day_price`、`max_nights` → `max_days`。
API の `nights` → `use_days`。すべて `use_start` 〜 `use_end` の**両端を含む日数**。

**理由**: 日帰りを受け付けると決めた時点で、0泊が正当な値になる。
泊数で数えると「0泊は無料なのか」が表現できない。実際、旧コードは

```js
const nights = diffDays(use_start, use_end) + 1;   // 実体は日数
const extra_nights = Math.max(0, nights - plan.nights);  // plan.nights は「泊数」
```

と**日数と泊数を同じ土俵で引き算していた**。8/23〜8/24 は1泊2日だが `nights = 2` と数えられる。
バグというより、要件で「どちらで数えるか」を決めていなかったことがそのまま出ていた。

**トレードオフ**: 日帰り（`use_days = 1`）でも `included_days = 2` の `base_price` を満額もらう。
実質これが最低料金になる。往復の配送が発生する以上は妥当だが、
日帰りを安く見せたいなら日帰り専用プランを `plans` に足す形になる。

### 4. 対応エリアを関東〜東海に絞った

**結論**: 関東1都6県（片道1日）＋ 山梨・静岡・愛知・岐阜・三重（片道2日）の12都県。

**理由**: 実機1台なので、遠方を1件受けるほど拘束日数が伸びて月の回転数が落ちる。
北海道（片道3日）だと 3 + 利用 + 3 + 整備1 で**1件に1週間以上**機材が張り付く。
SEO の主戦場も「テントサウナ レンタル 関東」なので、集客と在庫の両方から関東圏が正しい。

**トレードオフ**: 遠方の問い合わせを取りこぼす。ただし `shipping_zones` に行を足すだけで開けられるので、
2セット目を入れた時点（稼働率ゲート）に再判断すればいい。

## 見つかった穴 — 最小リードタイムが無かった

過去日チェックが `use_start` にしかかかっておらず、**発送日が過去になる予約が通っていた**。

```js
if (use_start < today())                          // 使用開始日しか見ていない
const lock_from = addDays(use_start, -zone.days); // ここが過去日になりうる
```

東京都（片道1日）で `use_start = 今日` は検証を通過し、`lock_from = 昨日` の行が `item_days` に書き込まれる。
**今日発送して今日届く予約が成立する。**

対面受け渡しなら起きなかった、配送固有の穴。`MIN_LEAD_DAYS`（＝1・最短で明日発送）を置き、
`lock_from >= today() + MIN_LEAD_DAYS` を `availability` と `bookings` の両方で検証するようにした。
エラーには `earliest_use_start`（その都道府県で最短いつから使えるか）を返す。

> 教訓: **バリデーションは入力そのものではなく、入力から導出した値にかける。**
> 過去日チェックの対象は `use_start` ではなく `lock_from` だった。

## 最終構成 — 1予約が押さえる日

```
配送先=東京都（片道1日）、9/6 に日帰り利用、整備1日の場合

  9/5        9/6      9/7          9/8
  SHIP_OUT   USE      SHIP_BACK    MAINTENANCE
  └────────── item_days に4行（MORZH-001）──────────┘
  lock_from                                   lock_to

  → 次に発送できるのは 9/9 から。9/9 発送の予約（利用 9/10）が最短。
```

```
lock_from    = use_start - zones.days
ship_back_to = use_end   + zones.days
lock_to      = ship_back_to + plans.turnaround_days
```

`dateRange()` は `from > to` なら空配列を返すので、`turnaround_days = 0` に切り替えても
`MAINTENANCE` が0行になるだけで、コードの分岐は要らない。

## 面接での言い方

> **Q. 在庫はどう管理していますか**
>
> 個体×日付を複合主キーにした占有台帳を持っていて、予約時にその期間ぶんの行を1トランザクションで
> まとめて INSERT します。1日でも埋まっていれば主キー違反で全体がロールバックするので、
> アプリ側に在庫チェックを書いていません。
>
> 押さえる期間は「顧客が使う日」ではなく「他のお客さんに回せない日」です。輸送型のレンタルなので、
> 前に発送日、後ろに返送日、さらに乾燥・整備の日が付きます。**配送日数の計算結果が、そのまま在庫ロックになる。**
>
> 代償は粒度が日単位に固定されることです。時間単位の予約に変えるなら作り替えになりますが、
> この事業は日単位のレンタルなので、そこは動かないと判断しました。

> **Q. バリデーションで気をつけたことは**
>
> 入力そのものではなく、入力から導出した値に対してかけるようにしました。
> 最初は「過去の日付は予約できない」を使用開始日に対してだけ書いていたんですが、
> 実際に押さえるのは配送日数ぶん前の発送日なので、今日から利用開始する予約が通ってしまっていました。
> 台帳に昨日の日付の行が入る、つまり物理的に不可能な予約が成立する状態です。
>
> 今は「発送日が最短リードタイムを満たしているか」で見ていて、エラーには
> その都道府県で最短いつから使えるかを返しています。
